# 评价系统统一语义底座

本文件定义 Parser、G1、G2、G3、报告和画布共同遵守的产品语义。它不复制各规则全文，也不代替飞书规则母表和法规参数表。

## 1. 权威来源与职责

- 规则定义、触发条件和法规来源：飞书规则母表、参数表、法规依据表。
- 本地实现状态与源文件索引：`docs/rule-implementation-status.json`。
- 可执行事实：当前代码与测试；历史审计文档只代表生成时快照。
- G1：数据、引用、几何和拓扑证据是否可靠。
- G2：在明确项目用途、地区和法规版本下检查法定要求。
- G3：检查平面是否具备基本功能和正常使用条件，不冒充法规结论。

当前产品执行范围以飞书规则母表的“规则状态”为准。本地只执行：

- G1：G1-007、G1-009、G1-012、G1-013、G1-019、G1-023。
- G3：G3-001、G3-002、G3-003、G3-025、G3-027、G3-031。

已取消规则不得生成评价卡或进入G1/G3汇总。历史规则函数可以暂时保留为底层测量、回归证据或迁移参考，但不能通过模块级数组重新注册到产品报告。

只读 3D Viewer 是独立展示层：它只可读取 Parser 的克隆数据，不能写回 JSON、`Parsed`、Evaluation Handoff 或共享几何；相机、图层、剖切、单层、爆炸、隐藏与漫游都不得改变 G1/G2/G3/S1 的输入、证据、状态或结论。评价卡片定位必须继续以二维画布为证据界面。无 `roof` / `roof-segment` 源数据时不得在 3D 中补造屋顶；任何展示默认值、派生根节点或资产加载降级都必须对用户透明呈现。

同一根因只保留一个主问题。其他规则引用证据或显示关联信息，不生成等价问题卡。

## 2. 对象与用途语义

- `Room Region` 是墙体边界派生的物理测量主体。
- `Zone` 用于表达用途和开放复合功能，不自动拆分 Room。
- `Door Portal` 表达 Room–Room 或 Room–Exterior 的可靠连接。
- `Item` 和 `Shelf` 的用途以规范化 `functionTags` 为准；名称、Category、style只用于显示、冲突诊断或兼容，不通过关键词猜用途。
- 未知 `functionTags` 不得被“看起来像”某对象替代。

对象移动属性：

- 固定：墙、柱、井道、固定洁具、固定设备、可靠固定柜体。
- 当前摆放参与检查：床、桌、沙发、床头柜、衣柜等；不得为了通过评价假设临时移动。
- 日常轻型可移动：普通椅、餐椅、办公椅、扶手椅、凳子、脚凳；不作为硬性通行或门扇阻断，但专项使用关系可以检查。

## 3. 开启与使用空间

家具、柜体、抽屉和电器的开启碰撞、最小人员使用空间以及三维实体碰撞由3D编辑器负责，平面评价器不再据此生成G1/G3结论。下面的数据结构仍可供3D编辑器、调试图层和历史测量复用，但不属于当前平面G规则执行范围。

Item资产和Shelf可以提供：

- `openingDirections`：局部 `front/back/left/right/up/down`，随对象旋转。
- `maxOpeningDepth`：最大开启深度。
- `minOpeningUseClearance`：最小人员操作空间。

数值随模型缩放：前后沿局部Z、左右沿局部X、上下沿局部Y。缺失、`null`或0表示明确不可开启，不表示数据未知。

平面几何必须分别保留：

- `minimumUsePolygon`：不开到最大时，紧贴对象的基本使用区。
- `openingPolygon`：从对象边缘开始的最大开启范围。
- `openedUsePolygon`：从最大开启范围末端开始的人员使用区。
- `fullUsePolygon`：开启范围与开启后使用区的总需求包络，用于完整开启评价。

开启范围与开启后人员使用区必须分开判定：`openingPolygon` 是刚体扫掠，任何非豁免实体相交超过统一几何容差即表示无法达到声明开启状态；`openedUsePolygon` 才按房间内可用比例和可达性判断人员能否站立、取放或操作。不得把两者合并后以单一面积比例放行门、抽屉或设备门碰撞。

若 Item 或 Shelf 显式提供上述开启字段，Parser和Handoff应忠实保留源数据；平面评价器不再对完整操作包络生成G级通过或问题结论，相关物理检查由3D编辑器负责。

G3-013已取消并从平面评价器移除。二维人员中心路径不能可靠代表隔着低矮家具伸手操作窗户的能力；窗户规范与安全要求由G2负责，窗扇碰撞、家具高度和三维触达由3D编辑器负责。

Room Navigable Space 必须同时提供“由实际 Door Portal 落点可达”的自由空间证据。下游规则不得从画布显示用的自由格坐标重新拼接连通关系；窗户、设备或其他接近检查必须复用导航层的可达结果。

S1-HPE 的生产二维路径例外地使用独立 Polygon Visibility Graph，但继续复用 RoomConnectivityGraph、RoomRegion、DoorPortal 和楼梯语义。其 0.20 m agent radius 只属于技术 clearance，不得解释为 G2/G3 法规或合格阈值。家具开启区、最小使用区和三维操作包络不得进入 HPE 障碍；当前没有 ground-occupancy 字段时，有可靠 footprint 的固定、普通摆放和轻型落地家具保守参与，车辆与语义不可靠对象不自动加入。卧室行为起点只由正式床 `functionTags` 识别，不得读取资产名称。

Door 可显式提供可选布尔字段 `isPrimaryEntrance`，Parser、Evaluation Handoff 与 DoorPortal 必须原样投影；该字段只表达主要住宅入口，不得用门名称补猜。S1-HPE 的主要归家起点使用唯一标记 Door 的住宅侧 landing；缺失时只允许唯一可靠住宅外门兼容回退。厨房目标是首次进入正式 SF01/SF02 Zone 与可通行区域交界的位置。卧室按每张正式床 Item ID 独立测量，床边候选复用 `resolvedRotationRadians` 的局部坐标变换：局部 Z 为床头→床尾，局部 X 两侧为正常下床侧；不得由世界 footprint 的长宽比推断方向。

S1-HPE v0.1 Demo 局部评分的 `effectiveResidentialIndoorAreaSquareMeters` 仅使用合法 `spaceFunctionCode`：应计入 Zone 必须与唯一可靠 RoomRegion 求有效几何交集，随后按楼层并集，禁止按 Zone 名称猜测或将开放重叠 Zone 重复相加。SF24、SF30、SF32、SF50+ 及未编码 Zone 不计入。该面积只用于 HPE 相对距离归一化，不改变 G1—G4 的面积、法规或使用性结论。

S1-FUR 不得另建家具碰撞或使用空间模型。它必须复用同一 `minimumUsePolygon`、`openingPolygon`、共享障碍豁免、Slab 越界和可达性子测量；家具关系的正式用途只由 `functionTags` 解析，`asset.category` 与名称仅用于显示和诊断。

默认画布顺序：`对象 → 蓝色虚线开启范围 → 绿色/红色开启后使用区`。

Shelf：

- `withBack=false` 的开放Shelf可从前后取物，显示两侧取物区，不显示虚构门扇开启区。
- `withBack=true` 只显示正面取物区。
- Shelf只有在显式提供开启字段时才显示蓝色开启范围。

## 4. 测量、状态与诚实性

- `measurementBasis=explicit`：直接使用可靠源字段。
- `measurementBasis=derived`：由可靠平面几何、拓扑或明确字段推导，必须记录假设和置信度。
- 派生结果远离阈值可以明确pass/issue；接近阈值仍保留结果并标记borderline。
- `unable_to_determine` 仅用于对象、关系或证据无法建立，且合理解释可能导致相反结论的情况。
- 不得为了减少unable虚构字段、边界、方向或对象身份。
- G2计算使用法规原始美制值精确换算；不得使用G3的400mm、人员半径或其他使用性参数作为法规阈值。

统一状态：`pass`、`issue`、`unable_to_determine`、`not_applicable`。依赖规则未解决可以保留内部blocked/dependency状态，但用户界面只由主规则报警。

## 5. 卡片、定位与颜色

- 首层卡片显示对象、实测、要求、原因和处理方向；源码ID与坐标放在技术详情。
- 通过项默认收起；issue和unable必须能切换正确Level并聚焦真实对象或Room。
- 缺失对象聚焦所属Room，不创建虚假对象。
- 问题主对象红色，关联对象橙色；蓝色虚线只表达开启几何，不表达通过或失败。
- 使用区绿色表示可用，红色表示不足，橙色虚线表示方向或证据待确认。
- 分类筛选G1/G2/G3时，卡片和画布高亮必须使用同一分类范围。
- 普通问题定位不展示寻路栅格、路径线、Portal采样点或Room锚点；这些计算证据保留在分析层和技术详情中。
- “显示400毫米基本通行范围”只显示由可靠Door Portal实际可达的人员中心区域，不显示未连接自由空间、全量障碍物或算法搜索过程。

## 6. 客户需求前置门槛

- Requirement Handoff 中的每条客户需求都是必须满足项，不再定义或显示“应当满足”、“期望满足”等优先级。
- 旧需求JSON中的`priority`字段仅作兼容输入忽略，不进入Requirement Handoff、G4结果或用户界面。
- 同一“开始检查”入口根据是否已加载Requirement Handoff决定执行流程：未加载时直接运行G1–G3；已加载时先运行G4。
- G4只有在全部结果为`pass`时才自动继续G1–G3。任一`issue`或`unable_to_determine`都暂停自动流程；后者必须明确显示“需要人工检查”，不得当作未满足。
- 暂停后用户可以主动选择“仍然继续完整检查”运行G1–G3；G4原始结果仍保留在统一报告中。
- G4的流程前置不改变领域编号；`G4-*`稳定规则ID、G1/G2/G3责任边界和既有结果保持不变。
- G4仍需先经过Parser、Evaluation Handoff、Room Region、Zone语义和Room Connectivity Graph证据准备；“前置”指用户产品流程前置，不表示跳过数据与空间证据构建。

## 7. 共享修改协议

以下修改属于跨G共享变更：对象语义、移动属性、Room/Zone/Portal定义、坐标与缩放、公共几何、状态语义、去重、问题卡和画布颜色。

提交共享变更时必须：

1. 更新本文件或`docs/evaluation-shared-change-log.md`；
2. 说明受影响的G组和规则；
3. 增加共享能力测试及受影响规则测试；
4. 运行`npm test`和`npm run build`；
5. 不通过修改冻结样例期望值掩盖非预期回归。

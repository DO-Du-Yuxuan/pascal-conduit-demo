## 结论摘要

Demo 已从单纯盒体预览前进到较完整的 source-node 显示：同层墙拼接与墙 CSG、曲墙、栏杆楼梯、坡屋面与天窗、柱/栏杆均有对应实现；屋面生成和 Fence 几何路径有对 `@pascal-app/viewer` 公共函数的直接调用，墙材质解析使用 core 公开材料解析器。Site ground/boundary、Shelf parametric parts、门窗细节和roof accessories仍有明确缺口。其它实现分为 Demo 几何、从 Builder 拷贝/适配的纯函数、或只保留外廓的近似代理。名字相同或 Studio 颜色相同不能证明渲染一致。

一个关键版本边界：Demo 的 `package.json` 锁定 `@pascal-app/core`、`@pascal-app/viewer` 为 **0.9.2**；Builder 本地源码是单独工作树。Demo 直接调用这些发布包的 `generateRoofSegmentGeometry`、`generateFenceGeometry`、roof frame 与 column primitive，只有实际安装的 0.9.2 包内容才是运行依据。对照 Builder 当前 source 而得的 parity 结论有源码版本漂移风险，建议整合前记录/锁定 dsphere commit 到 package 版本，并用同一组 node fixtures 对两个版本生成几何、材质组及 bbox 做比对。

同一问题会进入字段默认值：Demo 的 `builder-geometry.ts:2-19,22-38` 从发布包 import `RoofSegmentNode/SkylightNode/StairNode/StairSegmentNode`，再用 `.parse(...)` 生成 defaults；`builder-structural-geometry.ts:7-46` 对 Column/Fence亦从已安装 package schema `parse` 默认值，原始 node fields覆盖默认且不变异 raw node。它能避免把被解析 schema 的未知字段回写丢掉，却不会自动调用当前 dsphere registry `NodeDefinition.geometry/defaults/migrate` 里新增的定义或迁移。故需分清三件事：Demo passthrough保留合法JSON字段、0.9.2 schema defaults、当前 Builder definition/migration/defaults；三者并非同一个合同。整合要审这些字段的类型/缺省/单位/迁移，不要把 parse defaults “看起来同值”当作 source parity。

## 当前 Demo 展示边界

主 dispatch 在 `src/three/PascalScenePreview.tsx:328-356`：显式渲染 wall、slab、ceiling、beam、zone、item/shelf/cabinet/cabinet-module、door/window、column、fence、stair、roof-segment；stair-segment 由父 stair 生成；其他种类返回 `null`。Roof 是父容器，roof-segment 有实体几何；skylight 由父 roof segment 的子节点显示（`PascalScenePreview.tsx:361-389`）。因此“解析/保留或在 Scene tree 可见”并不等于建筑画布存在可见几何。`docs/unified-project-json.md:47,60` 描述项目节点所有权；`docs/3d-readonly-viewer.md:49-59` 与 `docs/builder-workspace-alignment.md:34-50` 是 Demo 当前承诺边界。未知/未实现节点继续保留 raw JSON，但不虚构实体模型。GLB 资产仍按合同延后。

Builder 的强制共有集合取自 `dsphere-main/packages/nodes/src/index.ts:2-28,46-81` 注册的 27 种 kind。以下矩阵只按这个集合判定共有缺项。`cabinet` / `cabinet-module` 是 Demo manifest 中额外的 legacy/发布 core kind，不属于当前 `builtinPlugin` 27-kind 集合；它们单列，不把它们算作 Builder 当前共有缺失。Demo 的 support manifest 标注来源 commit 为 editor `22c947...`（`src/coverage/pascalCoreManifest.ts:6-53`），不是本地 dsphere main 当前 builtin 集合，不能拿该旧清单当本次集合事实。

### Project 4.0 导入门槛会进一步收窄实际覆盖

上表的 kind 列以 Builder 注册集合核对，但“实现有 geometry helper”不等于 Project 4.0 导入后的真实 node 会走到该 helper。Demo `src/domain/unified-project.ts:7-8` 的 `BUILDING_TYPES` 只列 Site/Building/Level/Wall/Door/Window/Item/Shelf/Slab/Ceiling/Column/Fence/Beam/Roof/RoofSegment/Stair/StairSegment/Guide/Spawn/Zone/Elevator；decode 时只对这个 whitelist 中的大驼峰类型转为 kebab-case (`:217-222`)。它**不包含** Builder 当前 built-in accessories，如 `Skylight`, `BoxVent`, `RidgeVent`, `Chimney`, `SolarPanel`, `Dormer` 等。它们若在 Project 4.0 中以大驼峰类型直接导入，会作为原样 `Skylight` 等 passthrough type 保留；render dispatch却检查小写 `skylight` (`PascalScenePreview.tsx:371`) 并只在 RoofSegment child下渲染，因此 skylight几何 helper即使存在也不可达。同理这些 accessory不进入 `buildingLayerForType`/小写节点分支时不会画实体或执行 cut。该风险和 geometry parity 分开记：这是 Project decode/adapter coverage，不是缺少 skylight几何本身。应由项目数据/codec审计确定批准方式：扩充可识别的 Building accessory kind映射并保持原始 type round-trip，或明确保持不渲染/诊断；不能只在 Preview里 case-fold 来伪造一个节点类型，因为 raw JSON类型往返应稳定。

`builtinPlugin` 总表里共有其它 kind 归属：27个中以上未列在单独模型行的 `roof`, `stair-segment`, `site/building/level`, `scan/guide/spawn` 已覆盖。Demo `cabinet` 和 `cabinet-module` 额外情况见下面“扩展种类”。

## 重点主题差异

### 门窗参数解释、材质和宿主切口

Builder Door/Window 的 React node renderer 多是注册 hitbox，真实可见部件由 `DoorSystem`/`WindowSystem` 构造，而 operation animation store 可以覆盖持久 node 值。具体源证据：Door `packages/viewer/src/systems/door/door-system.tsx:1895-1953,2064-2250`；Window `packages/viewer/src/systems/window/window-system.tsx:3115-3215`，window animation source `packages/viewer/src/systems/window/window-animation-system.tsx:31-120,123-155`。Demo `Opening` 只有一个 meshStandardMaterial，window用角色玻璃 `#cdd8df` 及 opacity .25，door用joinery clay，见 `PascalScenePreview.tsx:242-253`；它没有从 `material`, `materialPreset`, `glassMaterial`, `frameMaterial` 等字段解析门窗材质，也没有 Builder sash animation store。

门窗洞是独立于视觉 node的 host boolean行为。Builder按 `openingKind` 区别 opening 与实际门窗；arch/rounded 使用对应 shape CSG，矩形普通门窗可从 host cutout子mesh取边界 (`wall-system.tsx:595-713`)。Demo opening geometry固定 box和 cutter fixed box；`position[1]`确实用作洞口垂直中心，缺省为半高，但它将 source `openingShape` 忽略。对曲墙，它将 along/chord长度占比转为 curve `t`，不是独立按曲线累计弧长；长曲墙开口的中心位置可能偏移。integration 应首先复用 Builder pure door/window mesh factories及 wall opening shape geometry，并把 runtime operationState当展示时态输入，不更改Project JSON。

### Wall miter / curve / CSG / 两侧材质

Builder Wall uses tagged miter boundary edges，不是只按face normal推测 interior/exterior。`assignWallMaterialGroups` 在各三角形附近找最近带标签边，再将朝下/端面/顶底归 base、两面归语义槽（`wall-system.tsx:206-307`）；frontSide/backSide默认 unknown，material group 退回 front=interior、back=exterior (`wall-system.tsx:194-204`)。Demo 当前 helper用曲/直wall tangent与footprint边界的 normal/material槽重分组（`builder-wall-geometry.ts:150-204`）；墙 material resolver调用 core的 `getEffectiveWallSurfaceMaterial`，支持 side override和legacy base fallback (`builder-materials.ts:70-83,121-179`)。有实用一致性，但一个依赖boundary标签、另一个以法向/方向分类，CSG新生成 face在复杂端头处可能进入不同槽。曲墙 Builder 3D边界会调用 inset函数；Demo曲线从自己的 wall helpers离散 footprint再挤出，且 cutter按矩形；因此连接/端修剪需使用真实 JSON fixture比较。

Builder 当前 Wall schema没有实际 trim-profile实体选项（`core/src/schema/nodes/wall.ts:9-44`）。`frontSide/backSide`是房间侧定义，不是左右装饰 trim开关。暂不能报告所谓 Builder 两侧 trim几何存在，也不能将两侧分组误称为已实现线脚。

### 材质、贴图、UV 与 Studio

Builder scene theme 是一组可选 theme数据，并不等于一个固定配色；`packages/viewer/src/lib/scene-themes.ts:3-25,27-129` 包括 Studio/Paper/Sunset/Overcast/Blueprint 等背景、地面、ambient/hemi/多灯/shadow、曝光和角色 clay tint。Demo `builder-presentation.ts:5-72` 只暴露固定 `studio` singleton。色值恰好从 Builder Studio 取样（wall `#e9e5db`、floor `#d8d2c4`、ceiling `#f1ede4`、roof `#c4bba6`、glazing `#cdd8df`）；这是真实角色外观近似，不是完整 theme系统。

Builder `packages/viewer/src/lib/materials.ts`维护材质与贴图缓存、wrap/repeat/rotation/flipY/channel/colorspace并可为 texture maps正确配置 (`:95-100,171-220,230-280`)。Demo `builder-materials.ts:113-179`能解析 Core MaterialSchema与墙面 library preset、role colors，Preview 的 `BuilderWallMaterialSlot` 通过 `TextureLoader`加载其 maps并repeat (`PascalScenePreview.tsx:32,67-105`)；但普通 material schema texture只建立 base map (`builder-materials.ts:162-179`)，preset maps才尝试多slot。Demo纹理路径是本地独立 loader，不共享 Builder缓存/UV体系/uv2处理。因此图片scale方向、texture channel、rotation/flipY与 lightMap AO烘焙可能不一致。

显式材质覆盖范围也分 node：Wall side schema/preset可见；Roof使用四槽 role mapping且per-segment explicit材质 (`PascalScenePreview.tsx:361-374`)；skylight frame/glass分材质 (`378-387`)；Stair所有几何parts共用 stair材质 (`256-266`)；Column/Fence node material用于所有 parts (`269-285`)；slab/ceiling Surface目前强制 Studio color (`337-338`, `Surface` 131-170)，Openings固定色 (`242-253`)，Item proxy固定 furnishing色 (`173-184`)。这些会使 source的合法角色材料在这些节点上被忽略。Builder roof generator明确保留UV2（`roof-system.tsx:762-813`），Demo canonical roof Boolean paths使用Evaluator的 `position/normal/uv`属性并在本地重建面组；是否保留 canonical `uv2` 需在 CSG结果确认。角色统一并不能证明 UV、法线、透明/双面、材质索引一致。

### 阴影、轮廓线与渲染管线边界

Demo presentation的Data记录 Canvas建议 `shadows=true`、PCF、ACES曝光（`builder-presentation.ts:65-72`），但 workspace UI实际 shadows 默认关闭且 session内开关：`ThreeDWorkspace.tsx:258,1282,2376-2393`；`BuilderLighting.tsx:4-23`只由 key light受 `shadowsEnabled`控制，其他 fill/ambient不投影。各建筑主mesh一般 cast/receive (`PascalScenePreview.tsx:262-285,372-374`)。Builder theme把 key lights/shadows作为theme数据 (`scene-themes.ts:15-24,27-47`)；不能从 `BUILDER_CANVAS_PRESENTATION.shadows=true` 推导Demo现状默认开启。

Demo `BuilderInk.tsx:38-83,126-152,172-240` 是对 Builder `packages/viewer/src/lib/ink-edges.ts:14-29,30-78` 的 **GLSL实现移植**：两边使用相同的 depth Laplacian、同一深度归一化/noise gate，以及 `normalEdge` 0.01/0.05阈值与 0.5/2.5 深度阈值。基础 ink检测算法不是外观猜测；主要实现差异在Builder用 TSL/Node graph接入postprocessing与共享depth+normal MRT，Demo用WebGL ShaderMaterial、独立beauty/normal/depth targets并自行控制render state (`BuilderInk.tsx:109-152,172-240`; Builder `packages/viewer/src/components/viewer/post-processing.tsx:265-281,339-420`)。Builder在ink后还叠加MergedOutlineNode提供selected/hovered的可见/隐藏轮廓及pulse (`post-processing.tsx:420-454`)，Demo没有等价选择/hover outline pass。Demo presentation.edge的 `thresholdAngle:20`不被GLSL消费；实际公式与Builder共用阈值，不是角度值。可能存在GLSL与TSL的buffer格式/精度、normal/depth attachment、色彩空间差异，但本次没作截图像素对照，标记为未验证的P3视觉风险；已确认差异是render-target/selection pipeline，不是ink数学逻辑。不要将它称为mesh edge overlay，也不要另加EdgesGeometry来替代semantic selection outlines。

`PascalScenePreview`只渲染 readonly building source nodes；Demo conduit/HVAC等系统模型由 `ThreeDWorkspace.tsx` 独立挂载的 `ConduitScene`、`HvacScene`及施工 Overlay生成 (`ThreeDWorkspace.tsx:2376-2642`)。Builder registered建筑/附件 renderer由 node definitions与systems拼装；它们不是Demo Construction Overlay合同，不能因demo pipe预览画面类似就把两套system geometry/编辑/碰撞/量测边界混为同一实现。Builder Ink当前作用于Canvas scene全体 mesh，可能包括demo系统管线；工程图2D SVG/标注/量测则是另一pipeline（`docs/3d-readonly-viewer.md:47-59`），本次建筑视觉审计不据此评价施工图输出。

## Demo额外种类（不在当前 Builder builtin 27-kind集合）

- `cabinet`, `cabinet-module`：Demo dispatch将其按 Item dimensions 画同一Box (`PascalScenePreview.tsx:341-345`)。因为当前 `dsphere-main/packages/nodes/src/index.ts` 27种kind未注册 cabinet，不能称其为 Builder 当前共享缺口；但 Demo导入/保留的旧项目可能有这些 legacy kind，当前画面仍无橱柜门板/抽屉/模块组合。Local Editor或历史发布包可能有实现，须以具体版本另审。
- Item真实asset mesh：盒形尺寸proxy为已约定的GLB延期范围；不要把该项写成现在必须整合模型资产。

## 集成优先级与建议复用路径

1. **Door/Window + opening cut shape**：视觉差异最大且 source 参数丰富。把 Builder door/window 的 pure geometry builders / opening shape builders抽到稳定公共 API；复用 `door-system.tsx` 与 `window-system.tsx` 中无Store部分，并让 Demo host CSG在相同 node输入下消费该 cutter geometry。需同时核对 parent/host transform、position[0]沿墙距离、position[1]垂直中心、曲墙t和operationState；只搬 renderer组件会拉入 store/hooks，不建议直接复制整个系统。
2. **Wall footprint + curved 3D trim/inset/material labels**：尽可能把 Builder 的 `getWallMiterBoundaryPoints`, `getWallSurfacePolygon/insetCurvedWallBoundaryPointsFor3D`, tagged boundary classification 与 opening cut helpers变成可调用的纯函数。Demo已经有 CSG fail-open+诊断、施工 chases/penetrations，应保留并做 adapter。两侧材料 group以Builder tagged edge算法为准。不要按现有frontSide命名臆造独立 trim产品字段。
3. **Ceiling/Slab**：复用 `generateSlabGeometry` / ceiling polygon normalization、material resolver和程序网格材质；为负slab、相交洞、圆管斜穿、ceiling侧面取拾取点做同fixture测试。不要更改domain的 elevation、测量 surfaces或实体施工孔。
4. **Roof accessories**：保留目前已直接调用的 canonical roof generator，升级 skylight boolean到 Builder accessory registry `capabilities.roofAccessory.buildCut`路径，复用 actual skylight geometry builder/material roles；对于 box vent/chimney/dormer/solar panel/ridge vent等应从 builder nodes公共 geometry接口补渲染及切口，否则做到“有子节点但不出画面”的诊断行为也比沉默更可靠。需校验 shader groups、uv2与door/window纹理朝向。
5. **Stair/Column/Fence**：Fence已用public generator；Column assembler和Stair/rail helpers目前是移植，应争取核心纯 geometry package exports并避免维护双份算法。先同源JSON的 bbox + segment/rail endpoints + face-group/material IDs比较，覆盖 `attachmentSide=left/right/front`、双landing、spiral direction、curved start angle、support/carving/cluster参数、Schema缺省值。
6. **材质主题/阴影/ink**：若目标是 Builder渲染 parity，应接入 Builder scene theme/material-cache API或明确仅冻结Studio；令材质角色通路覆盖 slab/ceiling/openings/stair/item proxy；统一 texture repeat/rotation/flip/colorSpace/channel/uv2。屏幕ink是当前有意设计选择，先将其作为 Demo渲染差异保留，对实际 screenshot/CSG进行调优，不要用几何边线替换来声称语义边线一致。

适合首批复用/抽取的 Builder 模块：`packages/viewer/src/systems/wall/wall-system.tsx` 纯 `generateExtrudedWall`周边的 footprint/tagged edge/cutout子函数；`packages/viewer/src/systems/door/door-system.tsx`、`window/window-system.tsx` 无store geometry factories；`packages/viewer/src/systems/slab/slab-system.tsx`、`ceiling/ceiling-system.tsx` polygon geometry；`packages/viewer/src/systems/roof/roof-system.tsx` 的 `generateRoofSegmentGeometry`、surface frame与cut accessory contracts；`packages/viewer/src/systems/stair/stair-system.tsx` stair/segment generators和 `nodes/src/stair/renderer.tsx` rail-path纯函数；`packages/viewer/src/systems/column/column-geometry.ts` primitives + Node renderer assembler；`fence-system.tsx` public generator（Demo目前已直接用）；`packages/viewer/src/lib/materials.ts`、`scene-themes.ts`。跨边界前需抽成无 store/hooks 的 public pure API。

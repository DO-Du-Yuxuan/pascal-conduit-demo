## JSON 到飞书字段映射

机器源文件为 `docs/rule-implementation-status.json`。

| JSON 字段 | 飞书字段 | 转换 |
|---|---|---|
| `ruleId` | 规则ID | 原值；同步业务主键 |
| `module` | 模块 | `G1` / `G3` 原值 |
| `ruleName` | 规则名称 | 仅初始化已确认名称；后续禁止自动覆盖 |
| `implementationStatus` | 实现状态 | `implemented` → 已实现；`partial` → 部分实现 |
| `executionType` | 执行方式 | 归一为自动、条件自动、人工复核或不执行 |
| `dataDependencies` | 数据依赖 | 数组连接为可读文本 |
| `bellevueStatus` | Bellevue结果 | `pass` → 通过；`issue` → 存在问题；`unable_to_determine` → 无法判断；`not_applicable` → 不适用；`not_run` → 未运行 |
| `limitations` | 当前限制 | 数组连接为可读文本 |
| `sourceFiles` | 代码文件 | 数组连接为仓库路径 |
| 无对应字段 | 技术文档 | 初始化为交接文档和机器规则清单路径 |
| 无对应字段 | 测试文件 | 仅在仓库中有明确测试证据时填写 |
| Git HEAD | 当前commit | 完整 commit SHA |

同步范围只包含机器清单中真实定义并注册的规则。未定义、未执行的编号不创建飞书记录。

## 同步边界

### Git 可以更新

- 实现状态
- 执行方式
- Bellevue 结果
- 数据依赖
- 代码文件
- 测试文件
- 当前限制
- 当前 commit

### Git 不得自动覆盖

- 规则名称
- 规则目的
- 产品状态
- V0.1 是否启用
- 通过标准
- 问题标准
- 设计师说明
- 产品决策
- 是否接受某个限制

无法识别字段、枚举转换失败、规则 ID 重复或目标记录不存在时，同步应停止并报告，不得新建近似字段、猜测值或按行号覆盖。

## 如何新增规则

1. 在飞书规则总表中确定规则 ID、正式名称、规则目的、产品状态和 V0.1 取舍。
2. 确认规则 ID 在全表唯一，并明确所属模块。
3. 在 Git 中增加机器规则条目、实现、测试和技术文档；未实现规则不得填写虚构代码或测试。
4. 自动同步只回写允许的技术字段。
5. 在案例测试表中建立至少一个对应案例；没有真实截图时附件字段留空。
6. 由产品和真实项目验收确认规则口径与实际可用性。

## 如何更新实现状态

1. 读取目标 Base 和规则总表的真实字段结构。
2. 用 `规则ID` 精确搜索目标记录，禁止依赖当前排序或行号。
3. 从 `rule-implementation-status.json` 获取实现状态、执行方式、依赖、Bellevue 结果、限制和代码文件。
4. 从仓库测试证据补充测试文件，并记录完整 commit SHA。
5. 仅更新允许的技术字段。
6. 回读该记录，核对产品字段未变化。
7. 运行自动化测试，并在需要时补充真实项目验收。

## 如何防止覆盖产品字段

- 同步程序采用字段允许名单，不采用排除名单。
- 更新请求只包含允许同步的字段，不发送整行记录。
- 以规则 ID 为唯一业务键；出现重复时立即停止。
- 写入前后保存产品字段摘要并比较。
- 枚举映射集中维护，未知值不自动创建新选项。
- 任何规则名称或 V0.1 取舍变化都必须由人工在飞书中确认。
- 批量同步先生成 dry-run 差异，再由用户确认写入。

## 是否值得开发自动同步脚本

在 G2 开发开始、规则数持续增长后，开发单向“Git 技术字段 → 飞书”的同步脚本是值得的。建议满足以下条件后再实施：

- JSON schema 和飞书字段枚举稳定；
- 规则 ID 成为不可变主键；
- 支持 dry-run 和逐字段差异；
- 使用字段允许名单；
- 能检测重复记录、未知枚举和缺失字段；
- 写入后自动回读验证；
- 不包含任何产品字段写权限。

当前只有 72 条规则且产品目录仍在演进，人工审核的受控同步比立即建设持续同步服务更合适。
